End to End Imitation Learning Pipeline

Dual UR3 (Universal Robots) robot · teleoperation → recording → conversion → π0.5 training → deployment
ROS 2Meta Quest (VR)π0.5 / openpi LeRobotPyTorch / JAXHDF5 FSDP trainingWeights & BiasesH100 / B300

Overview

This was the core of my internship. It is the pipeline that turns human demonstrations into an autonomous policy for the bimanual dual UR3 robot. Four stages feed a fifth: I teleoperate the robot to collect demonstrations, record them, convert them into a training dataset, and fine tune the model, which then gets deployed. I built the software for every stage, so a task idea could become a working autonomous behavior on the real robot.

The three camera streams the policy is trained and run on: the head camera plus the left and right wrist cameras, each resized to 224×224 before inference.

What I built

  • Teleoperation. A VR system that drives both arms and grippers in real time from a Meta Quest headset, over ur_rtde at 30 Hz. I designed the safety model: motion is off by default, the operator explicitly engages each arm, either arm can freeze on its own grip trigger, and two motion controllers can never fight for the same arm. I covered the engage logic with off robot unit tests.
  • Recording. A multi camera episode recorder that captures joints, grippers, and three synchronized camera streams. It paces on a self correcting timing grid and a freshness gate that guarantees zero duplicate frames, so the training data is clean and recorded at an honest, measured rate.
  • Data engineering. Converters from raw HDF5 recordings into the LeRobot format, plus the dataset library itself. I curated about 34 datasets and fixed real data quality problems: camera freezes, inverted wrist cameras, mixed resolutions and frame rates, and multi task merges.
  • Training. I fine tuned π0.5 (openpi) on remote H100 and B300 GPU clusters. I wrote the per robot input and output transforms and data configs, ran sharded (FSDP) training, and used Weights & Biases to track and analyze every run (loss and gradient curves) to decide which checkpoints to keep.

Results

  • Recorded 500+ demonstration episodes and trained multiple task policies that run autonomously on the real robot.
  • Standardized the datasets and trained models in the LeRobot format and saved them for the team to reuse, which set a repeatable procedure for future data collection and training.
  • The resulting policies were shown in the company’s live robot demonstrations.

Deployment and Edge Optimization

Serving trained policies to the robot · latency reduction · local and cloud inference
NVIDIA Jetson OrinA100 / A10RTX 5090 PyTorchJAXWebSockets Real time chunkingCUDAggml / GGUFA/B benchmarking

Overview

A trained policy has to run on the real robot fast enough to look smooth. I built the serving stack, then optimized it across cloud GPUs, a local box, and the robot’s own edge computer.

What I built

  • Serving architecture. A policy server and a robot client that talk over WebSockets. The GPU runs the model and streams action chunks, and the client feeds it observations and drives the arms.
  • Local and cloud inference on five GPU targets. I stood up serving on the robot’s own NVIDIA Jetson AGX Orin (PyTorch), a local RTX 5090 box that served the robot directly over the LAN with no SSH tunnel, a GCP A100, an Azure A10, and university H100 and B300 clusters. Each one had its own CUDA, driver, and GPU architecture to work around.
  • Custom deployment method, based on real time chunking. I developed my own deployment code, based on real time chunking (RTC), to remove the pause where the arm would otherwise freeze to think between action chunks. It runs inference in the background and splices in the next action chunk as it arrives, so the arm never stops. I implemented the guided chunk swapping from the RTC research and, while doing so, found and fixed a guidance sign error that had been missed.
  • Latency work. A per stage profiler that showed the real bottleneck was network jitter, not the model, plus a JPEG payload path that cut end to end latency roughly in half, from about 450 ms to 250 ms.
  • Edge study. I profiled inference on the Orin, found a Python GIL contention issue, and tuned the power modes. I also tested different quantization modes (Q8 and Q4) on a C++ (ggml) backend against PyTorch, with interleaved A/B tests, to see whether they would hold up on the robot.
  • World action models. Beyond π0.5, I deployed a family of world action models onto the same dual UR3 robot. I wrote the deployment scaffold and the entire Fast-WAM track (server, client, config, and profiler), and reverse engineered the model’s sync protocol from its server source.
  • Model evaluation. I tested the trained policies to decide which ones actually worked, running rollouts on the real robot and comparing checkpoints and training approaches, so the policies chosen for the live demonstrations were dependable.
  • Voice launcher. A simple way to start a demo by voice. It listens for a keyword in what the operator says and starts the matching task, so saying "medicine" starts the medicine task. Built with faster-whisper for speech to text and Piper for the spoken reply.

Results

  • A smooth, deployable serving path used for the live demonstrations.
  • The C++ backend was about 1.9× faster in isolation, but under real camera load the gap nearly vanished, so I made the evidence based call to keep the simpler PyTorch backend and avoid maintaining a second inference stack.
Measuring that an optimization does not pay off in the real setup was as useful as a speedup here. It saved the team from maintaining a second inference stack.

Applied Computer Vision

Robot plus a self hosted vision language model · reading printed labels · proof of concept
Qwen2.5-VLOpenCVllama.cpp vLLMA100Computer visionThreading

Overview

This is the computer vision side of my internship. The robot presents an object to a camera, a self hosted vision language model reads the printed text (an expiry date), and simple logic sorts the object as good or expired. The vision work is mine end to end: the camera pipeline, the image processing, and the reliability layer around the model.

What I built

  • Model serving. I ran a Qwen2.5-VL vision language model two ways: a quantized build on the edge device with llama.cpp, and a full build on a GCP A100 with vLLM.
  • Computer vision pipeline. I built the OpenCV image path, a fixed region crop and a Laplacian sharpness gate that rejects blurry frames before they reach the model. I split the work so the model only reads the raw text while Python parses the date and compares it.
  • Reliability. After analyzing live failures I added an anti hallucination layer: read confirmation, sanity windows on the year, and a burst that keeps the sharpest frame. I ran the slow model call on a background thread so it never stalled the robot’s control loop.
  • Camera and optics. I diagnosed a fixed focus camera that blurred at close range and swapped in an autofocus Arducam with a locked focus, which fixed the root cause of the bad reads.

Results

  • Reliable reads when the label is sharp and facing the camera, and fail safe by design: any doubt is treated as expired.
  • A working proof of concept for adding perception to a manipulation task with a general vision language model. It is not a production or medical grade system.

Sim-to-Real VLA Pipeline for Mobile ALOHA

Role: Simulation Team Member and Environment Developer
Advanced Computation and Artificial Intelligence (ACAI) Lab, Dr. Shengfeng Yang
January 2026 to Present
PythonMuJoCodm_controlLeRobot Jacobian-based IKVLA ModelsDomain RandomizationNSF ACCESS HPC

Overview

Training Vision-Language-Action (VLA) foundation models for manipulation requires large amounts of demonstration data, and collecting it physically is slow and expensive. This project builds a sim-to-real pipeline on the MuJoCo physics engine that generates thousands of diverse manipulation demonstrations for the 17-DOF Mobile ALOHA platform, providing multi-camera visual data and full-joint effort feedback.

Figure 1: High-fidelity MuJoCo simulation of the 17-DOF Mobile ALOHA platform.

Figure 2: Left-arm camera visual observation data generated for VLA model training.

My contributions

  • Kinematics and policy development: engineered four scripted policies for bimanual tasks including tube-picking and mid-air handovers, using a Jacobian-based damped-least-squares IK solver.
  • Advanced manipulation features: tube-position feedback to compensate for pendulum swing, grasp verification, and descent collision detection.
  • Domain randomization: a procedural system using dm_control to vary distractor objects, positions, and conditions so the model generalizes rather than memorizes a static scene.
  • Data pipeline and quality control: a dense episode-scoring system (Perfect → Catastrophic) that filters runs before export to the LeRobot format for training.

Figure 3: Procedurally generated distractor objects added to the workspace for domain randomization.

Results

  • Generates standardized datasets (joint states, velocities, efforts, and action commands) as structured training data for VLA fine-tuning.
  • Pipeline output is used to fine-tune pre-trained VLA models on NSF ACCESS HPC resources, reducing dependence on manual human teleoperation.
  • Fine-tuned VLA models and LLMs to automate bookshelf-organization tasks on the real Mobile ALOHA platform.

EPICS MOBI: USA Blind Hockey Prototype

Role: Design Lead and Electrical Team Member
Engineering Projects in Community Service (EPICS), Mobility (MOBI), Purdue University
August 2024 to May 2025
Fusion 360KiCadLTspice Polyurethane3D PrintingPCB DesignStructural Analysis

Overview

Developed with USA Blind Hockey through Purdue’s EPICS Mobility program. Current blind-hockey pucks use metal ball bearings for sound: they are heavy, injure players, and break after a single game. The goal was a reusable, safer puck that produces consistent sound from electronics rather than bearings while surviving competitive play.

Figure 4: Early CAD iteration of the snap-fit design; the team later moved to a threaded closure for durability.

Figure 5: The 3D-printed Polyurethane prototype, with the internal cavity for the electronic sound components.

My contributions

  • Directed a five-member team as Design Lead across the electrical and mechanical workstreams.
  • Electrical design: the puck’s internal electronics in KiCad (PCB) and LTspice (circuit simulation), engineered to survive severe impact without damage.
  • Mechanical design: Fusion 360 structural analysis to find weak points; iterated from a snap-fit to a threaded/screwed closure for durability and easy battery replacement.
  • Geometry & materials: redesigned sharp angles into filleted edges to distribute impact, and selected Polyurethane over PETG for impact resistance and low-temperature performance.
  • Ran real-user testing with a hockey player to validate durability, sound consistency, and waterproofing.

Results

  • The final Polyurethane prototype withstood 500 N of drop-test force while staying waterproof with consistent sound output.
  • Delivered a working proof-of-concept for a safer, reusable, multi-game puck.
Final prototype validated: 500 N impact resistance, consistent sound output, waterproof, tested with a real athlete.

The Nostradamus Project: Global Hurricane Predictor

Role: Creator and Developer · September to December 2024 · View on GitHub
PythonpandasFoliumOpenStreetMap API IBTrACS DatasetGeospatial MappingVectorization

Overview

  • A Python tool that processes the complete IBTrACS v04r01 dataset from NOAA, over 3 million cyclone track records from all ocean basins, 1842 to present (about 310 MB).
  • Given any city and month, it computes the historical probability of a hurricane passing within a 5-degree radius and classifies the risk from Very Low to Extreme.
  • Built in two iterations: a procedural version, then a refactor using vectorized pandas for much better performance.

Figure 8: An interactive Folium heatmap of global hurricane frequency in October, with a personalized risk marker placed in Miami, Florida.

My contributions

  • Geocoding module (location.py) using the OpenStreetMap Nominatim API to turn any city name into coordinates via HTTP requests and JSON parsing.
  • Probability algorithm using pandas boolean masking to filter by month and a ±5° bounding box, counting unique Storm IDs to find distinct hurricanes.
  • Vectorized refactor replacing loop-based counting with pandas operations (.nunique()) for significantly faster filtering.
  • Geospatial visualization with Folium and Branca: an interactive global heatmap with a color scaled legend and a risk classification tooltip.
  • Input validation and error handling for CSV loading and geocoding failures.

Results

  • Accurately processes 3M+ track records to output both a terminal risk classification and a navigable interactive HTML heatmap for any global location.
  • The refactored version showed measurable performance gains over the original by replacing row-by-row iteration with vectorized pandas filtering.
  • Full source and documentation are public on GitHub at Fabricio-Giusti/Nostradamus-Project.
